# 클라이언트-서버 구조

[01-network-basics.md](./01-network-basics.md) 8번에서 간단히 짚었던 클라이언트-서버 구조를 더 깊이 정리한다.

## 1. 클라이언트와 서버는 "역할"이지 "장비"가 아니다

- **클라이언트**: 요청(Request)을 보내는 쪽
- **서버**: 요청을 받아 처리하고 응답(Response)을 보내는 쪽

이 구분은 **상대적**이다. 브라우저는 API 서버 입장에서 클라이언트지만, 그 API 서버가 결제 API나 DB를 호출할 때는 그 서버 자신이 클라이언트가 된다.

```
[브라우저] --요청--> [내 서버] --요청--> [외부 결제 API]
   (클라이언트)      (서버이자 동시에 클라이언트)      (서버)
```

즉 실제 서비스는 클라이언트-서버 관계가 **여러 겹으로 이어진 체인**인 경우가 대부분이다.

---

## 2. 요청-응답 사이클 (Request-Response Cycle)

브라우저 주소창에 URL을 입력했을 때 벌어지는 일을 순서대로 따라가 보면 전체 그림이 잡힌다.

```
1. URL 해석 (프로토콜, 도메인, 경로 분리)
2. DNS로 도메인 → IP 주소 변환                  (→ 01-network-basics.md 6번)
3. 서버와 TCP 연결 수립 (3-way handshake)         (→ 01-network-basics.md 5번)
4. HTTPS라면 TLS handshake로 암호화 채널 수립      (→ 01-network-basics.md 7번)
5. 클라이언트 → 서버 : HTTP 요청 전송
6. 서버: 요청을 해석 → 필요하면 DB 조회/비즈니스 로직 처리
7. 서버 → 클라이언트 : HTTP 응답 전송 (HTML, JSON, 이미지 등)
8. 브라우저: 응답을 해석해서 화면을 그림 (HTML이면 파싱 후 렌더링, JSON이면 JS가 처리)
```

**핵심 포인트**: 이 사이클은 요청 하나마다 매번 반복된다. 페이지에 이미지 5개, API 호출 2개가 있다면 최소 7번의 요청-응답 사이클이 발생한다 (연결 자체는 재사용될 수 있지만).

## 3. Stateless와 "상태를 유지하는 것처럼" 만드는 방법

HTTP는 기본적으로 **Stateless(무상태)** — 매 요청이 독립적이고, 서버는 "이전에 이 사람이 뭘 했는지" 기억하지 못한다. 그런데 로그인 상태 유지, 장바구니 등은 "기억"이 필요하다. 그래서 아래 방법으로 상태를 흉내낸다.

| 방식 | 동작 | 저장 위치 | 특징 |
|---|---|---|---|
| **쿠키(Cookie)** | 서버가 응답에 `Set-Cookie` 헤더를 보내면, 브라우저가 저장했다가 이후 요청마다 자동으로 같이 보냄 | 브라우저 | 용량 작음(4KB), 자동 전송 |
| **세션(Session)** | 서버가 사용자별 상태를 서버 메모리/DB에 저장하고, 클라이언트에는 세션 ID만 쿠키로 내려줌 | 서버 (+ 클라이언트는 ID만) | 서버가 상태를 갖고 있음 → 서버를 여러 대로 늘리면(스케일 아웃) 세션 공유 문제 발생 |
| **토큰(Token, 예: JWT)** | 사용자 정보를 암호화/서명해서 토큰 자체에 담아 클라이언트가 보관, 매 요청마다 헤더에 실어 보냄 | 클라이언트 | 서버는 상태를 안 갖고 토큰 검증만 함(Stateless) → 서버 확장에 유리 |

```
쿠키 흐름:
1. 클라이언트 → 서버 : 로그인 요청
2. 서버 → 클라이언트 : Set-Cookie: session_id=abc123
3. 이후 모든 요청에 브라우저가 자동으로 Cookie: session_id=abc123 첨부
4. 서버는 abc123으로 "이 사람이 누군지" 세션 저장소에서 조회

토큰(JWT) 흐름:
1. 클라이언트 → 서버 : 로그인 요청
2. 서버 → 클라이언트 : { "token": "eyJhbGciOi..." } (본문으로 내려줌, 클라이언트가 직접 저장)
3. 이후 요청마다 클라이언트가 Authorization: Bearer eyJhbGciOi... 헤더를 직접 실어 보냄
4. 서버는 저장소 조회 없이 토큰 자체를 검증(서명 확인)해서 사용자 판별
```

> 세션은 서버가 "기억"하고, 토큰은 클라이언트가 "증명서를 들고 다니는" 방식이라고 비유하면 이해가 쉽다.

## 4. 계층형 아키텍처 (N-tier Architecture)

작은 프로젝트는 모든 로직이 서버 한 곳에 뭉쳐있지만, 규모가 커지면 역할을 계층으로 분리한다.

```
[Presentation Layer]   ← 클라이언트: 브라우저, 모바일 앱 (사용자에게 보여주는 부분)
        │  HTTP 요청/응답
        ▼
[Application Layer]    ← 서버: API 서버, 비즈니스 로직 (WAS, Web Application Server)
        │  쿼리
        ▼
[Data Layer]           ← 데이터베이스, 캐시(Redis) 등 (데이터 저장/조회)
```

- **2-tier**: 클라이언트가 DB에 바로 접근 (초기 데스크탑 앱 등, 요즘 웹에서는 거의 안 씀 — 보안/확장성 문제)
- **3-tier**: 클라이언트 - 서버(비즈니스 로직) - DB로 분리 (**현재 웹 서비스의 표준 구조**)
- **N-tier**: 서버 계층을 더 세분화 (API 게이트웨이, 인증 서버, 여러 마이크로서비스 등)

프론트엔드/백엔드를 분리해서 각각 배포하는 지금의 일반적인 웹 개발 구조가 바로 이 **3-tier**를 구현한 것이다.

## 5. 렌더링 위치에 따른 구조 (CSR / SSR / SSG)

"화면을 누가, 언제 그리는가"에 따라 클라이언트-서버의 역할 분담이 달라진다.

| 방식 | 동작 | 특징 |
|---|---|---|
| **CSR** (Client-Side Rendering) | 서버는 빈 HTML + JS만 내려주고, 브라우저(클라이언트)가 JS를 실행해서 화면을 그림 | 초기 로딩 느림(JS 다운로드 필요), 이후 페이지 전환은 빠름. SPA(React 등)의 기본 방식 |
| **SSR** (Server-Side Rendering) | 서버가 요청마다 완성된 HTML을 미리 그려서 내려줌 | 초기 로딩/SEO에 유리, 서버 부하는 더 큼. Next.js 등에서 지원 |
| **SSG** (Static Site Generation) | 빌드 시점에 미리 HTML을 만들어두고, 요청 시 그냥 파일을 내려줌 | 가장 빠름, 서버 부하 거의 없음. 콘텐츠가 자주 안 바뀌는 페이지(블로그, 문서 등)에 적합 |

```
CSR: 서버 --(빈 HTML + JS)--> 브라우저 --(JS 실행, 화면 그림)--> 사용자
SSR: 서버 --(완성된 HTML)--> 브라우저 --(그대로 표시 + JS로 상호작용 준비)--> 사용자
SSG: 빌드 시 미리 생성된 HTML 파일 --(그대로 응답)--> 브라우저
```

> 세 방식 모두 "클라이언트-서버 구조" 자체가 바뀌는 게 아니라, **HTML을 그리는 책임을 서버와 클라이언트 중 어디에 더 두느냐**의 차이다. (→ [../web-fullstack-roadmap/02-frontend-advanced.md](../web-fullstack-roadmap/02-frontend-advanced.md)의 Next.js 항목과 연결)

## 6. 서버 확장과 중간 계층

서비스 규모가 커지면 서버 한 대로는 감당이 안 돼서, 클라이언트와 서버 사이에 중간 장치들이 추가된다.

```
[클라이언트] → [CDN] → [로드밸런서] → [서버 1]
                                    → [서버 2]   ← 요청을 여러 서버로 분산
                                    → [서버 3]
```

| 구성요소 | 역할 |
|---|---|
| **로드밸런서(Load Balancer)** | 여러 서버 인스턴스에 요청을 분산시켜 한 서버에 부하가 몰리지 않게 함 |
| **리버스 프록시(Reverse Proxy)** | 클라이언트 요청을 대신 받아 내부 서버로 전달 (Nginx 등). SSL 처리, 정적 파일 서빙, 로드밸런싱을 겸하는 경우도 많음 |
| **CDN(Content Delivery Network)** | 이미지/JS/CSS 같은 정적 파일을 사용자와 지리적으로 가까운 서버에 캐싱해서 빠르게 전달 |

### 스케일링 방식

| 방식 | 설명 |
|---|---|
| **수직 확장(Scale-up)** | 서버 한 대의 사양(CPU, 메모리)을 높임 — 한계가 있고, 그 서버가 죽으면 전체 장애 |
| **수평 확장(Scale-out)** | 서버 대수를 늘림 — 로드밸런서 필요, 세션을 서버 메모리에 두면 문제가 생기므로 앞서 본 토큰 방식이나 외부 세션 저장소(Redis)가 유리해짐 |

## 7. 실시간 통신이 필요할 때

기본 HTTP는 "클라이언트가 물어봐야 서버가 답하는" 구조라, 서버가 먼저 클라이언트에게 알려주는(예: 채팅, 실시간 알림) 상황에는 한계가 있다.

| 방식 | 동작 | 특징 |
|---|---|---|
| **폴링(Polling)** | 클라이언트가 주기적으로 계속 요청해서 확인 (`setInterval`로 반복 호출) | 구현 간단, 불필요한 요청 많음 (실시간성 떨어짐) |
| **롱 폴링(Long Polling)** | 서버가 새 데이터가 생길 때까지 응답을 미뤘다가, 생기면 응답 | 폴링보다 효율적이지만 여전히 요청-응답 구조 |
| **WebSocket** | 한 번 연결을 맺으면 이후 클라이언트-서버가 **양방향**으로 자유롭게 데이터를 주고받는 별도 프로토콜 | 실시간 채팅, 게임 등에 적합. HTTP와 다른 지속 연결 |
| **SSE(Server-Sent Events)** | 서버 → 클라이언트 **단방향**으로 계속 데이터를 흘려보냄 | 실시간 피드, 알림처럼 서버발 업데이트만 필요할 때 WebSocket보다 간단 |

## 8. Monolith vs Microservices (구조 관점)

서버 자체를 어떻게 나누느냐의 문제. 클라이언트 입장에서는 보통 API 하나로 보이지만 내부 구조가 다르다.

| | 모놀리식(Monolith) | 마이크로서비스(Microservices) |
|---|---|---|
| 구조 | 하나의 서버 애플리케이션에 모든 기능 | 기능별로 독립된 여러 작은 서버 (주문 서비스, 결제 서비스 등) |
| 장점 | 개발/배포 단순, 초기 개발 속도 빠름 | 서비스별 독립 배포/확장 가능, 장애 격리 |
| 단점 | 커지면 전체가 얽혀 유지보수 어려움 | 서비스 간 통신 복잡, 운영 난이도 증가 |
| 적합 | 초기 스타트업, 소규모 팀 | 큰 조직, 트래픽/도메인이 명확히 분리되는 서비스 |

> 처음부터 마이크로서비스로 시작하는 건 대부분 과도한 설계다. 모놀리식으로 시작해서 필요해지면 분리하는 것이 일반적인 흐름. (→ [../web-fullstack-roadmap/06-advanced.md](../web-fullstack-roadmap/06-advanced.md)에서 아키텍처 항목과 연결)
